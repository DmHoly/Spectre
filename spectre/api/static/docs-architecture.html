Architecture technique

Cette page documente comment Spectre est construit, pour quiconque touche au code. Elle suppose une lecture du guide d'utilisation pour le vocabulaire fonctionnel.

Vue d'ensemble

Spectre est l'application métier qui relie deux bibliothèques Python indépendantes :

  • Follow — suivi d'expériences façon « git » : dépôt, commits immuables (Experiment), branches, tags, fusion, diff, DOE générique, graphe de filiation. Volontairement sans authentification ni notion de projet multiple.
  • StructureForge — simulateur 2D de procédé : substrat + étapes (dépôt, gravure, planarisation, lithographie, chimie) → géométrie de couches, rendu SVG.

Spectre n'écrit aucune logique de simulation, de diff, de DOE ou de versioning — ces deux bibliothèques sont importées telles quelles. Ce que Spectre ajoute : des comptes utilisateurs, plusieurs projets isolés avec des droits, et une interface unique et non technique qui orchestre les deux bibliothèques (« intégration métier », pas réécriture).

Règle de conception qui traverse tout le code : si une modification touche à la simulation, au diff ou au versioning eux-mêmes, elle appartient à StructureForge ou Follow, pas à Spectre.

Organisation du code

spectre/
  core/           # logique métier pure, sans FastAPI
    db.py           # sqlite3 (schéma, connexion) - la seule base relationnelle
    security.py      # hachage de mot de passe, sessions
    accounts.py       # comptes utilisateurs, réinitialisation de mot de passe
    projects.py         # projets, appartenance/rôles, invitations
    permissions.py       # require_role et résolution projet-depuis-l'URL
    structures.py         # ProcessLot, simulation, campagnes DOE, rendu SVG
    email.py               # envoi optionnel (log si SMTP non configuré)
  api/            # FastAPI : routes JSON + pages
    app.py          # create_app(), montage des routers et des pages statiques
    deps.py          # get_current_user (dépendance FastAPI)
    auth.py           # /api/auth/*
    projects.py        # /api/projects (liste/création/membres/invitations)
    structures.py         # /api/projects/{slug}/{materials,recipes,structures/*}
    experiments.py          # /api/projects/{slug}/experiences/*
    static/                   # une page = un fichier HTML + son JS dédié
  cli.py          # `spectre --host --port` (uvicorn)

Règle de dépendance : core/ ne connaît rien de FastAPI ; api/ résout la requête (projet, droits) puis délègue à core/ ou directement aux bibliothèques.

Modèle de données

Deux systèmes de stockage cohabitent, pour deux besoins différents :

DonnéeOù
Comptes, sessions, projets, appartenances, invitations, réinitialisationsSQLite (core/db.py), un fichier sous SPECTRE_DATA_DIR
Expériences d'un projet (versions, objectifs, preuves, conclusion...)Un dépôt Follow par projet, fichiers plats sous <data>/projects/<slug>/follow
Recettes personnalisées d'un projetUn fichier JSON par projet sous <data>/projects/<slug>/recipes.json

Follow et StructureForge stockent tout en JSON plat ; SQLite n'existe que pour ce qui a vraiment besoin de requêtes relationnelles (unicité d'un e-mail, appartenance à un projet, rôle). Un Repository Follow est reconstruit à chaque requête plutôt que mis en cache — il recharge depuis le disque à la construction, et Spectre sert potentiellement beaucoup de projets, pas un seul dépôt.

Le pont vers Follow

Le problème central : la Structure que Follow stocke (ProcessStructure, dans structureforge.adapters.follow_adapter) est la géométrie déjà aplatie — largeur de domaine + couches avec leurs contours. Elle ne permet pas de reconstituer les étapes d'origine (dépôt/gravure/angle/épaisseur) pour rééditer une structure déjà lancée.

Convention Spectre, sans toucher au schéma Follow : le procédé StructureForge original (substrat + liste d'étapes typées, en JSON) est stocké dans le champ libre Experiment.metadata, sous la clé "structureforge_process" (voir spectre/core/structures.py::process_metadata()). Pour faire évoluer une expérience, Spectre relit cette clé, préremplit le constructeur, laisse l'utilisateur modifier, resimule, puis commit via :

  • structureforge.adapters.follow_adapter.build_experiment() — premier lancement (équivalent d'un commit initial), retourne un ExperimentBuilder non committé pour que Spectre pose ses métadonnées avant .commit().
  • structureforge.adapters.follow_adapter.derive_experiment() — une évolution, équivalent de repo.derive() mais avec une nouvelle Geometry/liste d'étapes.

D'autres clés du même champ libre suivent le même principe : campaign_labels/campaign_factor_labels/campaign_factor_values (les libellés lisibles d'une campagne DOE, calculés une fois à la création plutôt que reconstruits à chaque lecture), objective_verification (le « comment vérifier » d'un objectif, un champ que follow.Objective n'a pas nativement), physical_tracking (identifiant/emplacement par échantillon).

Le modèle « évolution légère »

Un Experiment Follow est immuable une fois committé. Conclure, ajouter une preuve, poser une étiquette ou un suivi physique doivent donc chacun créer une nouvelle version — mais une version qui ne change qu'un seul aspect, en gardant tout le reste (structure, étapes, objectifs, statut, étiquettes, métadonnées) strictement identique à la version précédente.

Le motif, répété dans spectre/api/experiments.py pour conclure/preuves/etiquettes/entites/combiner :

builder = repo.derive(ref, title=parent.title, intent=parent.intent,
                       new_branch=_derive_branch(repo, parent, None), author=user.name)
builder.metadata = dict(parent.metadata)
builder.evidence = list(parent.evidence)
builder.tags = list(parent.tags)
builder.conclusion = parent.conclusion   # sauf conclure, qui remplace précisément ceci
# ... puis la seule modification propre à cet endpoint ...
experiment = builder.commit()

_derive_branch() mérite une explication : dériver directement sur la branche du parent échoue si ce parent n'est plus la pointe de sa branche (quelqu'un a déjà continué depuis) — Follow lève alors une erreur brute, en anglais, pleine de vocabulaire git, exactement ce que l'interface doit éviter. _derive_branch() détecte ce cas et dérive silencieusement sur une branche fraîche générée (structures.py::_unique_branch()) au lieu de laisser l'erreur remonter — l'utilisateur ne voit jamais la distinction, chaque action « légère » aboutit toujours à une nouvelle version affichée normalement.

Vocabulaire UI

Le jargon git de Follow ne doit jamais atteindre l'interface. Table de correspondance appliquée partout dans spectre/api/static/ :

Interne (Follow)Dans l'interface
commitenregistrer / version
dériver (derive)enregistrer une évolution
branchepiste (jamais nommée explicitement dans le flux principal — un nom est généré automatiquement)
fork / nouvelle brancheexplorer une nouvelle piste
mergecombiner (action avancée, repliée)
graphe de filiationfrise chronologique (fiche) / vue d'ensemble (page dédiée, avancée)

Deux endroits ont dû être corrigés explicitement pour une fuite de ce vocabulaire : le graphe Plotly de Follow (follow.presentation.graphing.build_graph_figure) étiquette nativement ses pointes de branche et son survol avec "branche: ..." — spectre/api/experiments.py::project_graph_html() retire cette trace et nettoie le texte de survol avant de servir la page. Et toute erreur remontée par un commit() Follow est traduite en message français générique plutôt que transmise telle quelle (voir « évolution légère » ci-dessus).

Droits

spectre/core/permissions.py::require_role(min_role) est une dépendance FastAPI : elle résout le projet depuis le slug dans l'URL, vérifie l'appartenance de l'utilisateur courant et son rôle, renvoie 403 sinon. Ordre des rôles : viewer < editor < owner. Chaque route déclare le rôle minimum requis via Depends(require_role("editor")) etc.

DOE et campagnes

Follow analyse génériquement des lots d'entités (follow.doe.batch.analyze_batch), mais StructureForge ne simule qu'une géométrie à la fois. Le pont : ProcessLot (spectre/core/structures.py), une follow.Structure qui contient une liste de ProcessStructure — le seul concept neuf que Spectre ajoute au modèle de données.

generate_campaign_variants() construit un plan croisé : VariantPlan.factors est une liste de VariantFactor (étape, champ ou estimation, valeurs), et chaque combinaison du produit cartésien de toutes les valeurs (itertools.product) devient une entité re-simulée. Un plan factoriel complet est toujours statistiquement identifiable — chaque facteur croise chaque autre par construction — donc rien à vérifier après coup, contrairement à un balayage « diagonal » construit à la main.

Paramètres process et estimations

Une étape de dépôt (structureforge.process.steps.Deposition) porte deux champs purement descriptifs, sans effet sur la géométrie (le même statut que ChemicalStep.parameters/.description) :

  • process_parameters: dict[str, float] — une grandeur du procédé (ex. {"flux": 12.0}).
  • derived_estimates: list[DerivedEstimate] — une relation linéaire définie par l'utilisateur (estimate = offset + coefficient * process_parameters[parameter]), avec son inverse (solve_parameter_for_estimate) pour en déduire le paramètre process nécessaire à une valeur cible.

Une campagne DOE peut faire varier soit le champ brut, soit une estimation nommée : VariantFactor.via_estimate déclenche _step_with_estimate_value() (spectre/core/structures.py) plutôt que _step_with_value(), qui résout le paramètre process par inversion avant de simuler chaque combinaison. Les libellés et valeurs affichés dans la feuille de split restent les valeurs cibles saisies (ex. un dopage), jamais le paramètre process sous-jacent.

Ces champs voyagent gratuitement à travers Spectre : process_metadata() sérialise chaque étape en JSON tel quel (step.model_dump(mode="json")), donc toute nouvelle propriété d'un type d'étape StructureForge est automatiquement conservée dans metadata["structureforge_process"] sans changement côté Spectre.

Comment étendre

Ajouter un type d'étape process

Le type appartient à StructureForge (structureforge/process/steps.py, union discriminée ProcessStep), avec sa logique de mutation de géométrie dans structureforge/process/simulate.py::_apply(). Côté Spectre, ajouter le nouveau kind à STEP_KINDS/STEP_ICON_PATHS et une branche dans renderKindFields()/buildStepFromForm()/fillKindFields() (structure-builder.js) suffit généralement — le reste (simulation, DOE, persistance) suit sans changement.

Ajouter une recette

Les recettes standard vivent dans structureforge.core.recipes.default_recipes() ; les recettes propres à un projet dans son RecipeStore (spectre/core/projects.py::get_recipe_store()), exposées via l'onglet « Structures » du projet et les routes POST/DELETE /api/projects/{slug}/recipes/{deposition,etch}.

Ajouter un endpoint « évolution légère »

Suivre le motif de la section « évolution légère » ci-dessus : dériver via _derive_branch(), copier tout ce qui ne change pas, remplacer uniquement le nouveau champ, traduire toute follow.FollowError en message français plutôt que de la laisser remonter.

Limites connues

Pas de retournement de structure (griding face arrière, flip-chip)

StructureForge modélise le substrat à sens unique : Geometry.substrate() pose un floor_nm (masse infinie protégée, jamais gravée ni recouverte), utilisé aussi bien par le dépôt que par la gravure pour ne jamais dépasser le fond du substrat (_bulk_pad/_clamp_floor dans geometry/engine.py). remove_floating_debris() ancre en dur sur self.layers[0].polygon — toujours la toute première couche déposée.

Retourner une structure (pour amincir ou graver la face arrière, coller une puce à l'envers) demanderait soit une transformation de coordonnées (miroir en y + recalcul de floor_nm) à chaque retournement, soit une deuxième frontière protégée symétrique à floor_nm — dans les deux cas, ça touche le dépôt ET la gravure, plus l'ancrage de remove_floating_debris() qui ne serait plus forcément layers[0] une fois la face d'origine posée contre autre chose. Aucun concept de face arrière n'existe aujourd'hui dans le code : ce serait un nouveau type de ProcessStep, avec des décisions de modélisation réelles à trancher avant toute implémentation (les motifs de la face d'origine, une fois enterrés, redeviennent-ils gravables une fois amincis jusqu'à eux ? comment floor_nm se redéfinit-il après un retournement ?).

Ce que Spectre sait faire aujourd'hui pour une intégration de type flip-chip : motifs de plots métalliques (dépôt + lithographie + gravure), vus dans Exemples : plots de report. Ce qu'il ne sait pas faire : le retournement lui-même, l'amincissement ou la gravure de la face arrière, le collage de deux structures l'une sur l'autre.

Tests

pytest dans chacun des trois dépôts (follow, structureforge, spectre). Côté Spectre, tests/conftest.py fournit une fixture client (un TestClient FastAPI avec SPECTRE_DATA_DIR pointé sur un répertoire temporaire par test — aucun état partagé entre tests). Chaque fonctionnalité a son fichier (test_campaigns.py, test_branching.py, test_physical_tracking.py...), généralement un flux complet via l'API JSON plutôt que des mocks.

Déploiement

Dockerfile à la racine de spectre/ : une seule étape, utilisateur non privilégié, données sous /data (variable SPECTRE_DATA_DIR, à monter en volume). docker-compose.yml pour un démarrage local. Variables d'environnement : voir le README.md du dépôt pour la liste complète (SPECTRE_DATA_DIR, SPECTRE_BASE_URL, SPECTRE_SMTP_*). Pas de pipeline d'intégration continue à ce jour.
