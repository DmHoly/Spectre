Architecture technique

Cette page documente comment Spectre est construit, pour quiconque touche au code. Elle suppose une lecture du guide d'utilisation pour le vocabulaire fonctionnel.

Vue d'ensemble

Spectre est l'application métier qui relie deux bibliothèques Python indépendantes :

  • Follow — suivi d'expériences façon « git » : dépôt, commits immuables (Experiment), branches, tags, fusion, diff, DOE générique, graphe de filiation. Volontairement sans authentification ni notion de projet multiple.
  • StructureForge — simulateur 2D de procédé : substrat + étapes (dépôt, gravure, planarisation, lithographie, chimie) → géométrie de couches, rendu SVG.

Spectre n'écrit aucune logique de simulation, de diff, de DOE ou de versioning — ces deux bibliothèques sont importées telles quelles. Ce que Spectre ajoute : des comptes utilisateurs, plusieurs projets isolés avec des droits, et une interface unique et non technique qui orchestre les deux bibliothèques (« intégration métier », pas réécriture).

Règle de conception qui traverse tout le code : si une modification touche à la simulation, au diff ou au versioning eux-mêmes, elle appartient à StructureForge ou Follow, pas à Spectre.

Organisation du code

spectre/
  core/           # logique métier pure, sans FastAPI
    db.py           # sqlite3 (schéma, connexion) - la seule base relationnelle
    security.py      # hachage de mot de passe, sessions
    accounts.py       # comptes utilisateurs, réinitialisation de mot de passe
    projects.py         # projets, appartenance/rôles, invitations
    permissions.py       # require_role et résolution projet-depuis-l'URL
    structures.py         # ProcessLot, simulation, campagnes DOE, rendu SVG
    email.py               # envoi optionnel (log si SMTP non configuré)
  api/            # FastAPI : routes JSON + pages
    app.py          # create_app(), montage des routers et des pages statiques
    deps.py          # get_current_user (dépendance FastAPI)
    auth.py           # /api/auth/*
    projects.py        # /api/projects (liste/création/membres/invitations)
    structures.py         # /api/projects/{slug}/{materials,presets-etapes,structures/*}
    experiments.py          # /api/projects/{slug}/experiences/*
    static/                   # une page = un fichier HTML + son JS dédié
  cli.py          # `spectre --host --port` (uvicorn)

Règle de dépendance : core/ ne connaît rien de FastAPI ; api/ résout la requête (projet, droits) puis délègue à core/ ou directement aux bibliothèques.

Modèle de données

Deux systèmes de stockage cohabitent, pour deux besoins différents :

DonnéeOù
Comptes, sessions, projets, appartenances, invitations, réinitialisationsSQLite (core/db.py), un fichier sous SPECTRE_DATA_DIR
Expériences d'un projet (versions, objectifs, preuves, conclusion...)Un dépôt Follow par projet, fichiers plats sous <data>/projects/<slug>/follow
Présets d'étape personnalisés d'un projetUn fichier JSON par projet sous <data>/projects/<slug>/presets_etapes.json, plus un fichier partagé entre tous les projets

Follow et StructureForge stockent tout en JSON plat ; SQLite n'existe que pour ce qui a vraiment besoin de requêtes relationnelles (unicité d'un e-mail, appartenance à un projet, rôle). Un Repository Follow est reconstruit à chaque requête plutôt que mis en cache — il recharge depuis le disque à la construction, et Spectre sert potentiellement beaucoup de projets, pas un seul dépôt.

Le pont vers Follow

Le problème central : la Structure que Follow stocke (ProcessStructure, dans structureforge.adapters.follow_adapter) est la géométrie déjà aplatie — largeur de domaine + couches avec leurs contours. Elle ne permet pas de reconstituer les étapes d'origine (dépôt/gravure/angle/épaisseur) pour rééditer une structure déjà lancée.

Convention Spectre, sans toucher au schéma Follow : le procédé StructureForge original (substrat + liste d'étapes typées, en JSON) est stocké dans le champ libre Experiment.metadata, sous la clé "structureforge_process" (voir spectre/core/structures.py::process_metadata()). Pour faire évoluer une expérience, Spectre relit cette clé, préremplit le constructeur, laisse l'utilisateur modifier, resimule, puis commit via :

  • structureforge.adapters.follow_adapter.build_experiment() — premier lancement (équivalent d'un commit initial), retourne un ExperimentBuilder non committé pour que Spectre pose ses métadonnées avant .commit().
  • structureforge.adapters.follow_adapter.derive_experiment() — une évolution, équivalent de repo.derive() mais avec une nouvelle Geometry/liste d'étapes.

D'autres clés du même champ libre suivent le même principe : campaign_labels/campaign_factor_labels/campaign_factor_values (les libellés lisibles d'une campagne DOE, calculés une fois à la création plutôt que reconstruits à chaque lecture), objective_verification (le « comment vérifier » d'un objectif, un champ que follow.Objective n'a pas nativement), physical_tracking (identifiant/emplacement par échantillon).

Le modèle « évolution légère »

Un Experiment Follow est immuable une fois committé. Conclure, ajouter une preuve, poser une étiquette ou un suivi physique doivent donc chacun créer une nouvelle version — mais une version qui ne change qu'un seul aspect, en gardant tout le reste (structure, étapes, objectifs, statut, étiquettes, métadonnées) strictement identique à la version précédente.

Le motif, répété dans spectre/api/experiments.py pour conclure/preuves/etiquettes/entites/combiner :

builder = repo.derive(ref, title=parent.title, intent=parent.intent,
                       new_branch=_derive_branch(repo, parent, None), author=user.name)
builder.metadata = dict(parent.metadata)
builder.evidence = list(parent.evidence)
builder.tags = list(parent.tags)
builder.conclusion = parent.conclusion   # sauf conclure, qui remplace précisément ceci
# ... puis la seule modification propre à cet endpoint ...
experiment = builder.commit()

_derive_branch() mérite une explication : dériver directement sur la branche du parent échoue si ce parent n'est plus la pointe de sa branche (quelqu'un a déjà continué depuis) — Follow lève alors une erreur brute, en anglais, pleine de vocabulaire git, exactement ce que l'interface doit éviter. _derive_branch() détecte ce cas et dérive silencieusement sur une branche fraîche générée (structures.py::_unique_branch()) au lieu de laisser l'erreur remonter — l'utilisateur ne voit jamais la distinction, chaque action « légère » aboutit toujours à une nouvelle version affichée normalement.

Vocabulaire UI

Le jargon git de Follow ne doit jamais atteindre l'interface. Table de correspondance appliquée partout dans spectre/api/static/ :

Interne (Follow)Dans l'interface
commitenregistrer / version
dériver (derive)enregistrer une évolution
branchepiste (jamais nommée explicitement dans le flux principal — un nom est généré automatiquement)
fork / nouvelle brancheexplorer une nouvelle piste
mergecombiner (action avancée, repliée)
graphe de filiationversions du procédé + historique complet (fiche) / vue d'ensemble (page dédiée, avancée)

Deux endroits ont dû être corrigés explicitement pour une fuite de ce vocabulaire : le graphe Plotly de Follow (follow.presentation.graphing.build_graph_figure) étiquette nativement ses pointes de branche et son survol avec "branche: ..." — spectre/api/experiments.py::project_graph_html() retire cette trace et nettoie le texte de survol avant de servir la page. Et toute erreur remontée par un commit() Follow est traduite en message français générique plutôt que transmise telle quelle (voir « évolution légère » ci-dessus).

Version de procédé (X.Y.Z) vs historique complet

Follow committe une nouvelle version immuable à chaque action - lancer, évoluer, conclure, ajouter une preuve, taguer... - sans distinguer un changement de structure d'une simple mise à jour de métadonnée : c'est délibéré, Follow ne sait pas ce que "structurel" veut dire pour un domaine qu'il ne connaît pas. Cette distinction est spécifique à StructureForge (un substrat + une liste ordonnée de ProcessStep) et vit donc entièrement côté Spectre, dans spectre/core/versioning.py - un calcul dérivé à la lecture, jamais stocké : rien de nouveau n'est écrit dans Follow, aucun endpoint de commit n'a changé.

classify_process_change(before, after) compare deux structureforge_process (substrat + étapes, voir spectre.core.structures.process_metadata) et classe le passage de l'un à l'autre :

  • majeur (X) - le substrat a changé, ou la liste des étapes a changé de forme (une étape ajoutée, retirée, ou l'ordre/la séquence des kind a changé).
  • mineur (Y) - même substrat, même forme d'étapes, mais au moins un champ autre que le name d'une étape diffère (un matériau, une recette, une épaisseur, une orientation...) - tout ce qui peut réellement changer la géométrie simulée.
  • correctif (Z) - la seule différence est le name d'une étape - un simple libellé, sans aucun effet sur la simulation (structureforge.process.simulate._apply ne lit jamais ce champ).
  • aucun - le procédé est identique bit à bit ; ce qui a changé sur ce commit (un tag, un titre, une preuve...) n'est pas un changement de structure/procédé.

compute_branch_versions(history) parcourt l'historique premier-parent d'une piste (reversed(repo.log(ref)), déjà utilisé par GET .../timeline) et assigne un X.Y.Z à chaque commit, y compris ceux classés "aucun" - qui héritent simplement du numéro de leur prédécesseur. GET .../timeline renvoie donc deux vues de la même piste : items (tout, numéro de version inclus, pour l'historique complet en bas de la fiche) et versions (uniquement les entrées dont le niveau n'est pas "aucun", pour la frise "Versions du procédé" au-dessus).

Le graphe de projet (project_graph_html()) applique la même idée à l'échelle du dépôt entier : determine_keep_ids() garde toujours une racine, une fusion (deux pistes qui se rejoignent restent visibles quel que soit leur contenu) ou la pointe d'une branche, et sinon ne garde un commit que s'il a fait bouger la version ; collapsed_dag() reconstruit ensuite le graphe en reliant chaque nœud gardé à ses plus proches ancêtres gardés, en traversant les commits retirés. Le résultat est passé à build_graph_figure(repo, dag=...), dont le paramètre dag (optionnel, None = repo.graph()) a été ajouté côté Follow spécifiquement pour ce besoin - Follow reste générique, il dessine simplement le graphe qu'on lui donne.

Droits

spectre/core/permissions.py::require_role(min_role) est une dépendance FastAPI : elle résout le projet depuis le slug dans l'URL, vérifie l'appartenance de l'utilisateur courant et son rôle, renvoie 403 sinon. Ordre des rôles : viewer < editor < owner. Chaque route déclare le rôle minimum requis via Depends(require_role("editor")) etc.

DOE et campagnes

Follow analyse génériquement des lots d'entités (follow.doe.batch.analyze_batch), mais StructureForge ne simule qu'une géométrie à la fois. Le pont : ProcessLot (spectre/core/structures.py), une follow.Structure qui contient une liste de ProcessStructure — le seul concept neuf que Spectre ajoute au modèle de données.

generate_campaign_variants() construit un plan croisé : VariantPlan.factors est une liste de VariantFactor (étape, champ, valeurs), et chaque combinaison du produit cartésien de toutes les valeurs (itertools.product) devient une entité re-simulée. Un plan factoriel complet est toujours statistiquement identifiable — chaque facteur croise chaque autre par construction — donc rien à vérifier après coup, contrairement à un balayage « diagonal » construit à la main.

Croissance épitaxiale vs croissance facettée

Deux étapes StructureForge pour faire croître un matériau plutôt que le déposer, complémentaires plutôt que redondantes :

  • EpitaxialGrowth avance la surface selon une seule orientation cristalline choisie (orientation) : c_plane (strictement vers le haut), m_plane (latéral, sur les flancs) ou semi_polar (incliné à angle_deg depuis l'axe c). Le bon outil pour un buffer/template en croissance pleine plaque, une coquille latérale (cœur-coquille), ou une facette à un angle physique connu. seed_materials (optionnel) active la sélectivité SAG : la croissance ne reprend que là où l'un de ces matériaux est exposé — ailleurs (masque SiO2/Si3N4 laissé en place, substrat...) rien ne pousse.
  • FacetedGrowth simule une vraie croissance épitaxiale multi-facettes, bas en haut : chaque application fait avancer simultanément trois familles de plans cristallins à leur propre vitesse relative — la plus rapide sur le plan C (rate_c, le sommet plat), plus lente sur les plans M (flancs verticaux, rate_m), et sur les facettes semipolaires qui émergent entre les deux (rate_sp, à semi_polar_angle_deg depuis l'axe c). C'est le rapport entre rate_c et la composante verticale de rate_sp qui décide si le sommet reste plat (C domine) ou se referme en pointe (SP domine) au fil de plusieurs étapes successives — sans qu'aucun angle final ne soit choisi à la main. seed_materials (optionnel) active la même sélectivité SAG qu'EpitaxialGrowth.

Géométriquement, Geometry.deposit_epitaxial()/deposit_faceted() (structureforge/geometry/engine.py) construisent la nouvelle pellicule comme la somme de Minkowski de la surface germe exposée avec le polygone de croissance (le segment ou le polygone de Wulff convexe des vecteurs de vitesse), moins le solide déjà existant — c'est ce qui produit sans if/else explicite les facettes de coin qui relient le sommet plan C aux flancs plan M. Cette somme s'applique à toute la surface germe exposée, pas seulement à son sommet : sur un pilier autoportant déjà haut, une seule application fait donc avancer les flancs sur toute leur hauteur (croissance en coquille), pas seulement près du sommet — appliquer plusieurs couches fines successives, une par période de puits quantique par exemple, est ce qui fait émerger une forme en crayon/pyramide qui se referme progressivement.

Sans seed_materials, la croissance reprend sur toute la surface solide exposée (cas non sélectif, buffer/template en pleine plaque). Avec, seule l'empreinte des matériaux germes non recouverte par un autre matériau contribue — une empreinte de germe vide (aucun germe encore exposé) fait silencieusement de l'étape un no-op plutôt que de lever une erreur, le cas attendu pour la toute première couche d'une séquence SAG avant qu'un germe n'existe.

Masque de lithographie périodique

Lithography.openings (structureforge.process.steps) reste une simple list[tuple[float, float]] — des plages en x, en nm, où le masque est ouvert. C'est déjà la bonne représentation pour un outil en coupe 2D : un « diamètre d'ouverture » y est simplement la largeur d'une ouverture, un « pas » (pitch) l'espacement centre à centre entre deux ouvertures consécutives. Aucun changement StructureForge n'était donc nécessaire pour un réseau périodique (trous, piliers, plots répétés à intervalle régulier) — seul le formulaire de l'étape en avait besoin.

Le générateur (generatePeriodicOpenings(), js/structure-builder/form-widgets.js) calcule la liste d'ouvertures à partir du pas, du diamètre, d'un nombre optionnel (vide = rempli automatiquement le domaine) et d'un décalage optionnel (vide = réseau centré dans le domaine) — puis écrit le résultat dans le même champ texte que le format manuel existant ("80-140, 300-360", lu par parseOpenings()). Pas de nouveau schéma, pas de lien vivant après coup : générer un réseau est un point de départ éditable, exactement comme un préset ou une structure de bibliothèque appliquée au formulaire.

Retournement de structure (face arrière)

L'étape Flip (structureforge.process.steps.Flip, kind "flip") retourne physiquement la structure pour travailler sa face arrière — amincissement, via traversant, contact métallique arrière — avant de retourner à nouveau si besoin. Elle ne porte aucun champ propre (juste un nom) : c'est Geometry.flip() (geometry/engine.py) qui fait tout le travail.

flip() fait deux choses : miroir vertical de chaque polygone de couche autour de la mi-hauteur du solide courant (pas autour de y=0) — les bornes globales et floor_nm restent donc numériquement inchangés, seul ce qui était « en haut » se retrouve « en bas ». Et self.layers est inversée en même temps, pour que layers[0] continue de désigner l'ancrage que remove_floating_debris() utilise comme référence — après un retournement, c'est ce qui se trouvait au sommet un instant plus tôt (maintenant collé au support), pas le substrat d'origine, qui flotte désormais librement au nouveau sommet comme le reste.

floor_nm ne sert qu'à supprimer un bord exposé artificiel à cet endroit (pour qu'un dépôt conforme ne fasse pas pousser un film accroché sous la structure, et qu'une gravure isotrope ne morde pas vers le haut comme si c'était de l'air) — ce n'est jamais un bouclier qui rendrait la matière réelle au-dessus immunisée contre la gravure. Un amincissement de face arrière suffisamment profond traverse donc légitimement jusqu'à la face avant enterrée, exactement comme une gravure ordinaire traverse un substrat plein étant donné assez de profondeur : rien ne protège cette matière au-delà de son épaisseur réellement modélisée — le comportement correct pour simuler un via traversant (through-wafer via) qui vient contacter un plot métallique de la face avant.

flip() exige une surface avant plane sur toute la largeur du domaine au moment de l'appel (vérifié en comparant l'aire d'une fine tranche juste sous le sommet à la largeur du domaine multipliée par son épaisseur) — sinon une topographie plus basse ailleurs dans le domaine ne serait pas réellement collée au support une fois retournée. C'est le pendant exact d'une pratique réelle : on planarise toujours une face avant avant de la coller sur un support temporaire, précisément parce que le collage a besoin d'une surface de contact plane. Une étape Planarization juste avant le Flip suffit à satisfaire cette contrainte.

Comment étendre

Ajouter un type d'étape process

Le type appartient à StructureForge (structureforge/process/steps.py, union discriminée ProcessStep), avec sa logique de mutation de géométrie dans structureforge/process/simulate.py::_apply(). Côté Spectre, tout ce qui est spécifique à un type d'étape (libellé, icône, formulaire, lecture/pré-remplissage du formulaire, résumé affiché dans la liste, paramètres éligibles à une campagne DOE, génération du code Python équivalent) est co-localisé dans une seule entrée de STEP_KIND_DEFS, le registre défini en tête de js/structure-builder/step-kinds.js — ajouter le nouveau kind revient à y ajouter une entrée ; le reste (structure-builder.html, simulation, DOE, persistance) suit sans changement.

Ajouter un préset d'étape

Un préset d'étape est un raccourci nommé côté Spectre vers une recette de dépôt ou de gravure StructureForge : chaque étape ne porte qu'un recipe: str (structureforge.process.steps.Deposition/Etch), résolu contre structureforge.core.recipes.RecipeLibrary au moment de la simulation, pas à la construction de l'étape. Les présets intégrés vivent dans spectre.core.step_presets.default_step_presets() (un par recette standard de structureforge.core.recipes.default_recipes(), même nom) ; les présets propres à un projet dans son StepPresetStore (spectre/core/projects.py::get_step_preset_store()/get_shared_step_preset_store()), exposés via la page dédiée /projets/{slug}/presets-etapes et les routes GET/POST/PUT/DELETE /api/projects/{slug}/presets-etapes. Choisir un préset dans le constructeur ne fait que préremplir le sélecteur de recette (wireRecipeField() dans js/structure-builder/form-widgets.js, alimenté par GET /api/projects/{slug}/recettes) — une fois l'étape ajoutée, elle ne référence plus le préset par nom, exactement comme une structure dérivée d'un préset de bibliothèque (voir « Le modèle "évolution légère" »).

Ajouter un endpoint « évolution légère »

Suivre le motif de la section « évolution légère » ci-dessus : dériver via _derive_branch(), copier tout ce qui ne change pas, remplacer uniquement le nouveau champ, traduire toute follow.FollowError en message français plutôt que de la laisser remonter.

Liens inter-projets

Chaque projet a son propre dépôt Follow (projects.follow_repo_path(slug)), et une follow.core.models.ReferenceLink est validée à la validation du commit pour toujours pointer dans ce même dépôt (repository.py, _commit) — impossible donc pour combiner/évoluer de relier deux projets directement, et Experiment.metadata (où vit par exemple physical_tracking) n'est lisible que du côté qui l'a écrit. spectre.core.links est la seule relation qui traverse quand même cette frontière : deux tables dans spectre.db plutôt qu'un objet Follow — project_links (deux project_id + une note) et entity_links (deux références projet + expérience + index dans physical_tracking — le même adressage que les noeuds « entité » de l'atlas, entity:{experience_id}:{index}). Ni l'une ni l'autre table n'a de clé étrangère vers Follow (rien dans spectre.db n'en a) : un lien vers une expérience ou un projet depuis supprimé devient une ligne orpheline que l'atlas ignore silencieusement plutôt qu'une erreur — entity_links en particulier n'a aucune contrainte d'intégrité du tout côté SQL, project_links se contente d'un ON DELETE CASCADE qui la nettoie si l'un des deux projets est supprimé.

Un lien se crée avec editor des deux côtés (POST /api/liens-projets, POST /api/liens-entites — spectre.api.links) : créer un lien affirme quelque chose sur deux projets à la fois, pas seulement le sien. Le retirer ne demande editor que d'un seul côté (on ne devrait pas avoir besoin des droits d'écriture sur le projet d'un collègue pour désolidariser son propre projet d'un lien devenu obsolète). GET /api/atlas ne renvoie que les liens dont les deux côtés sont visibles par l'appelant — un lien vers un projet dont on a perdu l'accès depuis disparaît silencieusement de l'atlas plutôt que de nommer un projet qu'on ne peut plus voir.

Cas d'usage d'origine : optimiser une structure de référence dans un projet (par exemple affiner un empilement PGaN) pendant qu'un autre projet optimise autre chose sur sa propre lignée, et vouloir noter que les deux se rejoignent - ce que spectre.core.links couvre (le lien référentiel, visible sur l'atlas, créé depuis le panneau contextuel d'un noeud projet ou entité). Ce qu'il ne couvre pas : une vraie fusion de contenu entre deux dépôts Follow distincts (reprendre les étapes/la structure d'une expérience d'un autre projet dans un combiner) - ça resterait un chantier séparé, plus lourd (il faudrait faire évoluer combiner/évoluer pour accepter une référence (projet, id) et dériver à travers deux dépôts Follow distincts, ce qui change la forme de _derive_branch et de ConcludeRequest/CombineRequest, qui supposent aujourd'hui un seul dépôt). Un lien référentiel documente que deux pistes se rejoignent ; il ne les fusionne pas.

Pièces jointes

Une mesure, une wafer map, un rapport (image/PDF/CSV/texte, 10 Mo maximum — ATTACHMENT_ALLOWED_TYPES/ATTACHMENT_MAX_BYTES, spectre.api.experiments) attachée à une étude entière ou à une entité physique précise, depuis le panneau contextuel du noeud correspondant sur l'atlas. image/svg+xml est délibérément absent de la liste : un SVG peut embarquer du <script>, un vecteur XSS stocké classique pour un fichier destiné à être réaffiché tel quel.

Comme les étiquettes ou le suivi physique, envoyer ou retirer une pièce jointe enregistre une nouvelle version Follow plutôt que de modifier quoi que ce soit sur place — la liste vit dans Experiment.metadata["attachments"], chaque entrée portant un entity_index optionnel (le même adressage que spectre.core.links : une position dans le physical_tracking brut de cette version, pas dans la liste déjà filtrée que l'atlas affiche - None pour une pièce jointe sur l'étude entière). Les octets envoyés vivent séparément sur disque (spectre.core.projects.attachments_dir()), nommés par un id généré plutôt que par le nom de fichier envoyé — filename/content_type/size vivent dans un petit sidecar JSON à côté, pour que le téléchargement (GET /api/projects/{slug}/pieces-jointes/{id}) n'ait jamais besoin de retrouver quelle version d'une expérience mentionne encore cet id. Retirer une pièce jointe ne supprime pas le fichier du disque : une version plus ancienne, immuable, peut encore la lister, et rien d'autre dans cette application ne supprime non plus le reste de l'historique.

Briques technologiques

Une brique (spectre.core.tech_bricks.TechBrick) est une séquence nommée d'étapes de procédé, sans substrat propre — l'analogue « séquence » d'un préset d'étape (StepPreset, une config d'une seule étape), de la même façon qu'une structure sauvegardée (SavedStructure) est l'analogue « séquence + substrat ». Même stockage à deux niveaux que les présets d'étape et la bibliothèque de structures (KeyedJsonStore via projects.get_tech_brick_store()/get_shared_tech_brick_store(), deux fichiers JSON — projet et partagé), mêmes routes CRUD sous /api/projects/{slug}/briques-technologiques (spectre.api.structures, réutilisant list_three_buckets/reject_duplicate/require_existing de .keyed_resource).

Composer une brique réutilise le constructeur de structure lui-même plutôt qu'un éditeur d'étapes séparé — un troisième mode aux côtés du mode bibliothèque et du mode expérience (isBrickMode dans js/structure-builder/context.js, câblage dans brick-mode.js), qui masque les sections propres à une expérience (campagne, objectifs, lancement) mais garde le substrat affiché à titre de prévisualisation seulement — il n'est jamais envoyé à l'API ni enregistré avec la brique, qui s'appliquera sur la structure existante au moment de l'insertion, quelle qu'elle soit. Insérer une brique (contrôle dans step-list.js, à côté de « + Ajouter une couche ») copie une version clonée de ses étapes dans state.steps à la position courante — même philosophie « point de départ, pas de lien vivant » que partout ailleurs dans la bibliothèque de structures et les présets : modifier les étapes insérées ensuite n'affecte jamais la brique enregistrée, et réciproquement.

Limites connues

Pas de collage de deux structures distinctes l'une sur l'autre

Le retournement de structure (amincissement/gravure/contact de la face arrière après un Flip) est supporté — voir Retournement de structure. Ce qui reste hors de portée : coller deux Geometry simulées séparément l'une sur l'autre (un vrai collage de wafer, où chaque face vient de son propre historique de procédé). Geometry ne modélise qu'une seule pile continue ; un collage à deux structures demanderait de fusionner deux piles indépendantes en une seule, avec ses propres décisions de modélisation (alignement, interface de collage, quel floor_nm gagne) qui n'ont pas été tranchées.

Ce que Spectre sait faire aujourd'hui pour une intégration de type flip-chip complète : motifs de plots métalliques (dépôt + lithographie + gravure, voir Exemples : plots de report), et depuis peu le retournement + traitement de la face arrière (amincissement, via traversant, contact arrière). Ce qu'il ne sait toujours pas faire : coller la structure retournée sur une seconde structure simulée séparément.

Pas de vraie fusion de contenu entre deux projets

combiner/évoluer ne savent dériver ou fusionner qu'à l'intérieur d'un seul dépôt Follow (follow_adapter.derive_experiment() prend un ref qui doit déjà exister dans le repo qu'on lui passe). Ce que Spectre sait faire entre deux projets aujourd'hui : comparer en lecture seule (experience_diff_external, « Comparer avec » sur la fiche) et documenter qu'une piste se rejoint avec une autre (Liens inter-projets, visible sur l'atlas). Ce qu'il ne sait toujours pas faire : reprendre réellement les étapes/la structure d'une expérience d'un autre projet dans un combiner, comme on le ferait avec deux lignées du même projet - voir Liens inter-projets pour ce que ça demanderait.

Sécurité

Corrigé : échappement HTML incomplet dans escapeHtml() (XSS stockée)

escapeHtml() (static/js/common.js) échappait &/</> mais pas les guillemets, alors que tous ses appelants l'utilisent pour insérer une valeur dans un attribut HTML entre guillemets doubles (value="...", data-name="...", href="..."). Un nom de structure, de préset d'étape ou une URL de preuve contenant un " sortait donc de l'attribut. Vérifié en conditions réelles : un simple éditeur de projet peut créer une structure nommée x" onmouseover="…", dont le JavaScript s'exécute chez n'importe quel autre membre du projet (y compris lecture seule) qui survole le bouton correspondant dans l'onglet Structures — sans clic requis. Corrigé à la source (la fonction échappe maintenant aussi ' et ") plutôt que dans chaque appelant.

Durcissement possible, non fait

  • Pas de limitation du nombre de tentatives sur /api/auth/login ni sur /api/auth/mot-de-passe-oublie — un compte peut être attaqué en force brute à débit lent.
  • Le cookie de session (spectre_session) n'est pas marqué Secure — sans incidence en HTTP local, mais à activer si l'application tourne derrière HTTPS.

Vérifié correct (pas juste supposé)

Mots de passe hashés PBKDF2-SHA256 (200 000 itérations) avec comparaison à temps constant ; cookies httponly/samesite=lax ; chaque route API passe par require_role() (core/permissions.py), vérifié route par route — aucune route sensible sans contrôle de droits ; experience_diff_external (comparaison inter-projets) vérifie l'accès aux deux projets avant de renvoyer le diff, pas seulement celui de l'URL ; les slugs de projet sont assainis ([^a-z0-9]+ retiré) avant de servir de nom de dossier — pas de traversée de chemin possible ; les liens envoyés par e-mail (réinitialisation, invitation) utilisent SPECTRE_BASE_URL en configuration, jamais l'en-tête Host de la requête ; l'image Docker tourne en utilisateur non privilégié.

Tests

pytest dans chacun des trois dépôts (follow, structureforge, spectre). Côté Spectre, tests/conftest.py fournit une fixture client (un TestClient FastAPI avec SPECTRE_DATA_DIR pointé sur un répertoire temporaire par test — aucun état partagé entre tests). Chaque fonctionnalité a son fichier (test_campaigns.py, test_branching.py, test_physical_tracking.py...), généralement un flux complet via l'API JSON plutôt que des mocks.

Déploiement

Dockerfile à la racine de spectre/ : une seule étape, utilisateur non privilégié, données sous /data (variable SPECTRE_DATA_DIR, à monter en volume). docker-compose.yml pour un démarrage local. Variables d'environnement : voir le README.md du dépôt pour la liste complète (SPECTRE_DATA_DIR, SPECTRE_BASE_URL, SPECTRE_SMTP_*). Pas de pipeline d'intégration continue à ce jour.
